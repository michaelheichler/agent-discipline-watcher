The two clauses cover different failures, recency catches old evidence and the newest-row guard catches recent evidence belonging to the wrong run, so neither is redundant and neither may be deleted. Put precisely: recency bounds how old the pinned evidence itself may be, while the any-row check confirms nothing more current exists anywhere in the ledger than what is pinned, and recency does not imply freshness relative to other sessions. Every time comparison in this gate, the staleness guard, the recency window, and the block-to-release ordering, compares instants, never strings: timestamps parse with datetime.fromisoformat, naive treated as UTC, so a timezone-offset ts can neither sort a release above a block it precedes nor let a stale pinned session outrank newer rows from the current one, and a malformed ts raises naming the bad string. The marker semantics still back the comparison, a release row is written only by a passing stop_hook_active retry, which the client sends only after a block. Accepted residual: if the operator skips the pin step and the current run writes no ledger rows at all, a stale pin naming a session still inside the two-hour window can pass, which is why the pin write with rm -f is the first step of the procedure and why the live human observation of the block and the release remains the backstop, this case is bounded by the window and the newest-row guard, not closed.
